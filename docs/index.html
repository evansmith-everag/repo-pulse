Is code moving? Is anything waiting on you?

Repo Pulse is a live dashboard for up to three GitHub repositories under any organization or user your token can see. It shows the pull requests that need review, the checks on the branch you watch, the latest release, and what landed this week, on one page that updates itself.

  • No dependencies, no build step
  • Node.js 22 or newer
  • Windows, macOS, Linux, Docker
  • Talks only to GitHub

Is anything waiting on me?

Each card counts the open, non-draft pull requests that nobody has approved or asked changes on, with the age of the oldest one. Beneath it, Oldest open lists the three oldest with author, review state, and a marker for first-time or community contributors.

main ● passing main ● failing canary ● running

Is the branch green?

A chip reports the checks on the branch you watch; a failing card also gets a red top edge. When checks failed this week, the card says how many passed and failed, which workflow is failing now, and links to the latest failed run. Open Dependabot security alerts appear on the card too, when the token may read them.

main · last commit 20m ago · release 1.141.0 6d ago

What shipped, and what is landing?

The meta line gives the branch, the age of the last commit, and the latest release with its age. Commits and merged pull requests for the last seven days sit above it, with a seven-bar shape of the week. The velocity table compares each number with the seven days before.

What is on the page

Everything comes from GitHub's API on each poll; nothing historical is stored on the server.

Checks on the watched branch

The chip reads main ● passing, ● failing or ● running; repositories with no checks show no chip. Watch a branch other than the default by writing name@branch; commits, the checks chip, the week's shape and the last-commit age follow that branch.

Review state

A counts line per card: PRs open, approved, changes requested, drafts, issues open, untriaged issues (open, no label, no comments), and the open-issue count for each label you choose, up to five, such as bug or help wanted.

Releases and the week's shape

The latest release with its age, the last commit's age, and seven bars for the last seven days of commits. Quiet (no commit in 30 days), Slowing (8 to 30 days), Archived or Unavailable chips appear when they apply. Active repositories get no chip; silence is the good state.

Velocity table

Per repository with a totals row, arrows against the seven days before: Merged, Opened, Cycle time (median open-to-merge), First review (median open-to-first-review), Commits, People (and the busiest one's share; 75 percent or more is highlighted), Issues +/−, Stale PRs (older than 14 days), CI failed out of total runs, and Alerts. Bots are left out of the people column and the medians. Hover a heading for its definition, or open the definitions list under the table.

Recent commits, live

Up to five of the latest commits per repository, merged newest first. Open pages get each new snapshot over server-sent events; new rows are tagged new and changed numbers show their delta, for example ↑2, until the next update. Browser notifications for new pull requests and failing checks are a per-browser option.

TV mode

Add ?tv=1 to the address on a wall display: the layout fills the screen, type is larger, the commit feed moves inside each card, and the navigation is hidden. TV mode defaults to dark; &theme=light forces light.

Your token stays yours

The server reads the token once at startup from GITHUB_TOKEN, GH_TOKEN or the GitHub CLI login. It never shows the token anywhere; it tells you which source and which account are in use. The only network traffic is to GitHub: api.github.com for polling, plus the release download when you press Update now.

Stays live, backs off politely

After a failed poll the interval doubles, up to 30 minutes. A rate-limit answer pauses polling until the time GitHub gives. The last snapshot is kept on disk, so a restart shows data immediately. If a page loses the server it says so and reconnects on its own.

Updates itself

The server checks this project's releases shortly after it starts and about once a month. When a newer one exists, the dashboard shows the version, a link to the release notes and Update now. Updating verifies the SHA256 checksum, replaces the files in place, keeps the previous copies in .previous/, and exits so the start script, systemd or Docker brings it back.

How it works

Three steps. The dashboard itself lists them until all three are done.

  1. Download and start

    Install Node.js 22 or newer, download the latest repo-pulse-vX.Y.Z.zip and unzip it. On Windows, double-click start.cmd. On macOS or Linux, run sh start.sh. Anywhere: node server.js. The start scripts open http://127.0.0.1:4317 in your browser.

  2. Give it a token

    Set GITHUB_TOKEN (or GH_TOKEN), or sign in with the GitHub CLI (gh auth login) and the server uses that login. Public repositories need no scopes. The console prints which token it is using and for which account, for example token: GitHub CLI login (gh auth token) as @you.

  3. Pick repositories

    Open Settings, enter an organization or user (or press Use my account), press Load repositories, pick up to three, and save. Type owner/name for a repository under another owner and name@branch to watch a branch other than the default. One dashboard can mix organizations.

One Settings tab, nothing to configure twice

Shared settings live in config.json next to server.js: the owner, the repositories, the poll interval (15 seconds to 1 hour; 60 seconds by default), and up to five issue labels to count. The file can be edited by hand while the server is stopped; if it cannot be parsed, the server starts with defaults, leaves the file alone, and shows the problem in Settings.

Preferences that belong to one person live in the browser, not in the shared settings: theme (system, light, dark), reduce motion, hide commits by bots, announce changes to screen readers, browser notifications, and whether the velocity table is shown. Keyboard: r refresh, p pause, d dashboard, s settings, t theme, v velocity table.

Set MAX_REPOS to pick up to nine repositories. Three is the glanceable number; more repositories mean a slower poll.

TV mode for the wall

Open http://127.0.0.1:4317/?tv=1 on the display. The cards fill the screen, the numbers get big enough to read from across the room, the latest commits sit inside each card, and the navigation, the status buttons and the tables are hidden. It defaults to dark; add &theme=light to force light. If the display is another machine, run the server where that machine can reach it: keep it on loopback behind a reverse proxy, or bind it to 0.0.0.0 only when nothing fronts it, and set ADMIN_TOKEN so viewers cannot change settings.

What leaves your machine

Short list. The server has no dependencies and the page has no third-party scripts, fonts or analytics, so there is nothing else to account for.

api.github.com
Each poll makes two GraphQL requests in parallel, one for the cards and one for the velocity searches, plus one REST call per repository for its Actions runs. That is about 2 points of the token's 5,000-points-per-hour GraphQL budget; the status strip shows what is left.
your token
Read once at startup from GITHUB_TOKEN, GH_TOKEN or gh auth token, and sent only to api.github.com. It is never shown anywhere; the console, the setup steps and the Settings tab say which source and which account are in use. For public repositories a token with no scopes is enough.
update checks
Shortly after start and about once a month, the server asks GitHub's releases API for this repository; that is the only request the checks make. UPDATE_CHECK=0 turns them off. Pressing Update now downloads the release zip and SHA256SUMS from GitHub and verifies the checksum before anything is replaced.
nothing else
The page uses system fonts and the server sends a strict content security policy, so the browser makes no request except to its own server. Bound to 127.0.0.1 by default, the server rejects requests whose Host header is not a loopback address or in ALLOWED_HOSTS, and rejects state-changing requests that a browser marks as cross-site, so other websites open in your browser cannot read or change anything.
on disk
config.json (settings) and snapshot.json (the last fetched data, so a restart shows data immediately) next to server.js. Velocity is computed fresh on every poll; nothing historical is kept. Browser preferences stay in that browser.
who can see it
Anyone who can reach the server sees the dashboard for the chosen repositories, fetched with the server's token. Set ADMIN_TOKEN so that changing settings and browsing an owner's full repository list need the token.

Run it

The release zip holds server.js, public/, the start scripts, package.json, the README and the license. The Dockerfile builds from the same files.

From the zip

1. Install Node.js 22 or newer
2. Unzip repo-pulse-vX.Y.Z.zip
3. Windows: double-click start.cmd
   macOS, Linux: sh start.sh

The start scripts open http://127.0.0.1:4317 in your browser and start the server again after an update. No chmod needed.

From a terminal

node server.js   # or: npm start

Set GITHUB_TOKEN in the shell first (export on macOS and Linux, set in cmd, $env: in PowerShell), or run gh auth login. The server prints the address and which token and account it is using. PORT and HOST change where it listens; keep HOST on loopback behind a reverse proxy.

Docker

From a clone of the repository:

docker build -t repo-pulse .
docker run -d --name repo-pulse --restart unless-stopped -e GITHUB_TOKEN=… -p 127.0.0.1:4317:4317 -v repo-pulse-data:/data repo-pulse

Settings and the cache live in the /data volume; the container reports health through /healthz. There is no gh inside the image, so the token comes from the environment.

For a team

Keep the server on loopback and put a reverse proxy with HTTPS (and ideally your SSO) in front of it. Set ADMIN_TOKEN so viewers cannot change settings, and run with ALLOWED_HOSTS naming the public host. Caddy keeps the Host header and streams server-sent events as is:

pulse.example.com {
    reverse_proxy 127.0.0.1:4317
}

For nginx, add proxy_set_header Host $host; (or run with TRUST_PROXY=1) and proxy_buffering off; so the event stream is not buffered. The README has a systemd unit for a Linux box, Raspberry Pi or NAS, and the Windows Task Scheduler equivalent.

Questions

Which token does it use, and what access does it need?

In this order: GITHUB_TOKEN, GH_TOKEN, then gh auth token from the GitHub CLI. For public repositories any token works: a classic token needs no scopes, a fine-grained token needs only the default public read access. For private repositories: a classic token with the repo scope, or a fine-grained token with read access to Contents, Issues, Pull requests and Metadata for the repositories you pick. Add Actions read access for the CI column and Dependabot alerts read access for the Alerts column; without them those columns show a dash. The token is read once at startup, so restart after rotating it.

Does it ever show my token?

No. It tells you which source and which account are in use, in the console at startup, in the setup steps, and in the Settings tab. The gh login is convenient but usually carries more scope than this tool needs; if that bothers you, create a read-only fine-grained token and set GITHUB_TOKEN.

How much of my GitHub API budget does it use?

Each poll costs about 2 points of the token's 5,000-points-per-hour GraphQL budget plus one REST call per repository from the separate 5,000-per-hour REST budget. The status strip shows the GraphQL points left. Polling runs every 60 seconds by default; the Settings dropdown offers 15 seconds to 1 hour. GitHub answers in about 4 to 6 seconds for busy repositories.

Can I mix organizations, or watch a branch that is not the default?

Yes. Each entry is name (under the organization or user you entered), owner/name (any other owner), or either with @branch. Commits, the checks chip, the week's shape and the last-commit age follow that branch; PR, issue and merged counts are for the whole repository. The same grammar works in config.json: { "org": "my-org", "repos": ["api", "web@release/2.x", "partner-org/sdk"] }.

What happens when a poll fails, GitHub rate-limits the server, or the token expires?

After a failed poll the interval doubles (with jitter) up to 30 minutes. A rate-limit answer pauses polling until the time GitHub gives, and the bar says when polling resumes. A rejected or expired token stops polling; the dot turns red and a banner says what to do, and Refresh now still retries. If the data is older than two poll intervals, an amber bar says how old it is and the cards dim. If the velocity request or an Actions call fails, only those cells go blank; the cards still update.

How do updates work, and can I roll back?

The server checks this project's GitHub releases about ten seconds after it starts and then about once a month, and says so in the console. When a newer release exists, the dashboard shows a bar with the version, a link to the release notes and an Update now button; Settings has the same plus Check now. Updating downloads the release zip and SHA256SUMS, verifies the checksum, replaces server.js, public/index.html, package.json, README.md and LICENSE in place, keeps the previous copies in .previous/, and exits with code 75; the start scripts, systemd and Docker's restart policy bring it back, and a hand-run node server.js needs starting again. To roll back, copy the files from .previous/ over the current ones and restart. Inside the Docker image it says to pull the newer image instead; inside a git checkout, git pull instead. A release that needs a newer Node.js than the one running is refused until you install it.

Can I run it for a whole team?

Yes: loopback plus a reverse proxy with HTTPS, ALLOWED_HOSTS for the public host name, and ADMIN_TOKEN so viewers cannot change settings or browse the owner's full repository list. Optional webhooks (WEBHOOK_SECRET and a GitHub webhook at https://<host>/webhook) refresh within a few seconds of a push; the server checks the signature and ignores replayed deliveries. Webhooks need the server to be reachable from GitHub, so they only work on a web server, not on localhost.

Is this a DORA or engineering-intelligence tool?

No. It shows the last seven days against the seven before, for a few repositories, computed fresh from GitHub on every poll; it keeps no history and knows nothing outside GitHub. It is probably not the right tool if you need trends over months, if you watch many repositories (three by default, nine at most, and more repositories mean a slower poll), or if you need data from GitLab, Jira or per-person reporting across an organization.

Can scripts or monitors read the data?

GET /api/snapshot returns the same JSON the page receives, with an ETag; send If-None-Match to get a 304 when nothing changed. GET /healthz returns 200 when the token works and data has been fetched, otherwise 503, which suits Docker health checks and uptime monitors. GET /api/update returns the running version and the latest release seen.
